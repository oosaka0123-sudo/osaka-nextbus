# data/ ディレクトリについて

このアプリのデータは4つのJSONファイルに分離されています。
**アプリ本体(index.html / css / js)を一切変更せずに、このファイルだけを
差し替えることでデータを更新できます。**

```
data/
├── metadata.json    データの出典種別・最終更新日
├── stops.json       停留所(名前・緯度経度)
├── routes.json      各停留所を通る系統・方面
└── timetable.json   各系統の発車時刻表(1日分・毎日繰り返し)
```

選択の流れは **停留所 → 系統番号 → 方面・行先 → 次のバス3便** の4段階。

**現在の状態(2026-08-29時点):**
`stops.json`(大阪シティバス停留所 992件)・`routes.json`(停留所×系統番号 1915件)
は国土数値情報 P11 2022年度版から抽出した実データ、`metadata.json` の
`dataSource` は `"manual"` です。ただし **P11データには系統の行き先・方面の
情報が含まれていない** ため、`routes.json` の label/destination には
系統番号(例: `"27号"`)をそのまま使っています。`timetable.json` はまだ空
`[]` のため、方面・行先・発車時刻はすべて未入力です。次のバス表示は
すべて「🚧 時刻表データ準備中」と表示されます(架空の時刻・行き先は
一切表示しません)。

`stops.json` が空、または `metadata.json` の `dataSource` が `"demo"` の場合は、
自動的に `js/data.js` 内蔵のデモデータ(停留所6件)にフォールバックし、
画面右上に「DEMO」バッジが表示されます。

## 実データへの切り替え方法(スマホだけでも可能)

1. `stops.json` / `routes.json` / `timetable.json` を下記の形式で実データに置き換える
   (GitHubのWeb UIの `Add file → Upload files` または直接編集で可能)。
2. `metadata.json` の `dataSource` を `"demo"` 以外の値(例: `"manual"`)に変更し、
   `lastUpdated` を更新した日付(`YYYY-MM-DD`)に変更する。
3. commit / push する。

これだけで、次回アプリを開いたときに実データが使われ、DEMOバッジは自動的に
消えます(`dataSource` が `"demo"` のまま、または `stops.json` が空のままだと
安全のため引き続きデモ動作になります)。

系統・方面・時刻表がまだ整備されていない停留所・系統・方面は、架空の時刻を
表示する代わりに自動的に「🚧 時刻表データ準備中」と表示されます。
系統・方面ごとに準備が整った時点で `timetable.json` を追記すれば、
その方面だけ次のバス表示が有効になります(全件揃える必要はありません)。

## ファイル形式

### metadata.json

```json
{
  "dataSource": "demo",
  "lastUpdated": "2026-08-29",
  "note": "任意の説明文(表示はされません)"
}
```

- `dataSource`: `"demo"` ならデモデータで動作。それ以外(`"manual"` 等)かつ
  `stops.json` が空でなければ実データとして採用される。
  将来 GTFS-JP / GTFS-RT を利用する場合は `"gtfs-jp"` / `"gtfs-rt"` 等、
  好きな文字列に変更してよい(アプリ側は `"demo"` かどうかしか見ていない)。
- `lastUpdated`: 画面上部に「最終更新 2026/08/29」のように表示される
  (`YYYY-MM-DD` 形式で入力する)。手動更新のたびに必ず変更すること。

### stops.json

```json
[
  { "id": "daikokucho", "name": "大国町", "lat": 34.6596, "lon": 135.4991 }
]
```

- `name` / `lat` / `lon` は必須。`id` は任意(省略時は名前+座標から自動生成)。
  複数の変換実行をまたいで安定させるため、`convert-ksj-p11.mjs` は
  名前+座標のハッシュから決定論的なIDを生成する(配列の並び順に依存しない)。

### routes.json

停留所ごとに、そこを通る系統番号を列挙する(行き先・方面はここには含めない。
それは timetable.json 側で扱う)。

```json
[
  { "id": "daikokucho__27号", "stopId": "daikokucho", "label": "27号", "destination": "27号" }
]
```

- `id`: アプリ全体で一意な系統ID(timetable.json の `routeId` から参照される)。
- `stopId`: `stops.json` の `id` と一致させる。
- `label` / `destination`: 現時点では系統番号をそのまま入れる
  (`label` はプルダウン表示用、`destination` は未使用に近いが同じ値でよい)。

系統が1件も無い停留所は、アプリ側が自動的に「時刻表データ準備中」の
ダミー系統1件を補って表示するため、`routes.json` に何も書かなくてよい。

### timetable.json

**系統(routeId) × 方面・行先** の組み合わせごとに1エントリとし、
その中に平日(weekday)・土曜(saturday)・休日(holiday)それぞれの
発車時刻の配列を持たせる。

```json
[
  {
    "id": "daikokucho__27号__namba (省略可)",
    "routeId": "daikokucho__27号",
    "direction": "なんば方面",
    "destination": "なんば行",
    "weekday":  ["05:31", "05:43", "05:55", "24:10"],
    "saturday": ["05:40", "06:05"],
    "holiday":  ["05:50", "06:15"]
  }
]
```

- `routeId`: `routes.json` の `id` と一致させる。
- `direction`: プルダウンに表示する方面名(例: `"なんば方面"`)。**必須。**
- `destination`: 次のバス表示欄に大きく表示する行き先(例: `"なんば行"`)。**必須。**
  direction・destination のどちらかが欠けている行は、架空の行き先を
  表示しないためアプリ側が自動的に無視する(行き先が分かるまでは
  そのエントリ自体を追加しないこと)。
- `weekday` / `saturday` / `holiday`: それぞれ `"HH:MM"`(24時間表記)の配列。
  **昇順に並べること**(CSV変換ツールを使えば自動で並び替えられる)。
  該当する曜日区分のダイヤがまだ分からない場合は、その配列を省略するか
  空配列 `[]` のままにしてよい(その曜日だけ「時刻表データ準備中」表示になる)。
- **深夜0時をまたぐ便**は `"24:10"`(=翌日00:10)、`"25:05"`(=翌日01:05)
  のように24時以降の表記で入力する(実際のバス停の時刻表でよく使われる
  表記そのまま)。アプリ側が自動的に実時刻(00:10, 01:05等)に変換して表示する。
- 平日/土曜/休日の判定は日本時間の暦日ごとに行われ、日曜日および
  内閣府の祝日基準(振替休日・国民の休日を含む)による祝日は「休日」、
  土曜日は「土曜」、それ以外は「平日」として扱われる。

**同じ系統番号でも上り/下りや行先が複数存在する場合**は、`routeId` が
同じで `direction`/`destination` が異なるエントリを複数追加すればよい
(例: 「なんば方面」行きと「玉出方面」行きを別エントリにする)。

系統に方面が1件も無い場合、または選択したカレンダー種別(平日/土曜/休日)に
該当する時刻が向こう8日以内に1件も無い場合は、アプリが自動的に
「時刻表データ準備中」と表示する(架空の時刻は一切表示しない)。

## データの出典に関するルール

このディレクトリに投入するデータは、**合法的に利用可能な公開データ、または
自ら現地で確認した情報など、正当な手段で得たデータのみ**を出典としてください。

- 大阪シティバス公式サイトや「い・ま・ど・こ？」(Bus-Vision)等のスクレイピングは禁止。
- 非公開API・利用規約違反となるAPIの利用は禁止。
- 停留所の名称・位置は、国土交通省「国土数値情報(バス停留所データ / P11)」等の
  オープンデータを優先する。年度違いのデータが複数公開されているため、
  年度を必ず確認すること(2022年度=令和4年度版のページ例:
  https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-P11-2022.html)。
- 系統・時刻表は、現時点で正式なオープンデータが確認できていないため、
  現地の時刻表掲示など正当な手段で確認した内容を手動で入力する運用とする。
  大阪シティバスへの正式なデータ提供の問い合わせ結果を待って、
  GTFS-JP / GTFS-RT が利用可能になり次第切り替える予定。

## 実データへの変換ツール

`scripts/convert-ksj-p11.mjs` を使うと、国土数値情報(P11)のGeoJSONから
`stops.json` 形式への変換ができます。`--routes-field` / `--routes-output` を
追加すると、系統番号を含む `routes.json` も同時に生成できます
(KSJ P11には行き先・方面の情報が無いため、label/destinationには
系統番号がそのまま入る)。使い方はスクリプト冒頭のコメントを参照してください。

事業者名は年度・整備時期によって表記ゆれ(「大阪シティバス株式会社」
「大阪シティバス㈱」「大阪市高速電気軌道株式会社」等)がありうるため、
変換前に `--list-operators` で実際の表記を確認してから `--operator` の
値を決めること(スクリプト内のコメントに手順あり)。

なお2022年度(令和4年度)版の大阪府データで実際に確認した結果、
大阪シティバス(株)の表記ゆれは無く(「大阪シティバス（株）」の1種類のみ、
992件)、系統番号は1フィールド(`P11_003_01`)にカンマ区切りで複数格納
されている形式だった(992停留所すべてに1件以上の系統が付与されており、
停留所あたり最大22系統)。P11データには系統の行き先・方面の情報が
含まれていないため、timetable.json は別途手動で用意する必要がある。

## 時刻表(timetable.json)をCSVから作る

`scripts/timetable-csv-to-json.mjs` を使うと、スマートフォンの表計算アプリ
(Googleスプレッドシート等)で作った時刻表CSVを `timetable.json` に変換できる。
1行=1便の「ロング形式」で、実際のバス停の時刻表を上から順に転記していく
イメージで入力できる。

CSVの列(ヘッダー行に以下を含める。順序は自由):

```
routeId,direction,destination,calendar,time
daikokucho__27号,なんば方面,なんば行,平日,05:31
daikokucho__27号,なんば方面,なんば行,平日,05:43
daikokucho__27号,なんば方面,なんば行,土曜,06:00
```

- `calendar` は `平日`/`土曜`/`休日`(または `weekday`/`saturday`/`holiday`)。
- `time` は `"HH:MM"`。深夜0時をまたぐ便は `"24:10"` のように24時以降で入力してよい。

変換コマンド:

```bash
node scripts/timetable-csv-to-json.mjs --input timetable.csv --output data/timetable.json
```

同じ (routeId, direction, destination) の行は自動的にまとめられ、
weekday/saturday/holiday の配列に振り分けられて時刻順に並び替えられる。
**direction/destination/calendar/time のいずれかが空の行や、calendar の
値が不正な行があると、変換を中断してエラー内容を表示する**(架空データを
作らないため、不完全な行を自動的に補完したり無視したりはしない)。
